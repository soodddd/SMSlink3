# 测试 Agent 升级报告

本文总结本轮 Android 模拟器回归测试中遇到的主要问题，重点列出最耗时、最反复出现、最容易误判的平台/业务问题，并给出对应解决办法与可执行的 Agent 升级建议。

## 1. 测试目标与范围

- 目标：在 `1-level` 的两台模拟器上完成配对、解除配对、重新配对、重连回归验证。
- 环境：Android Emulator + adb + logcat + uiautomator + Gradle Debug Build。
- 验证方法：
  - 先做设备健康检查
  - 再做发现 / 配对 / 解除 / 重连闭环
  - 每一步必须保留日志和 UI 证据

## 2. 最耗时的问题

### 2.1 模拟器身份与业务 ID 对不齐

问题表现：
- UI 上能看到发现到的设备，但配对时反复出现 `Device ID mismatch`。
- 同一台模拟器在不同会话里看到的 `deviceId` 不稳定。
- shell 侧拿到的 `ANDROID_ID`、relay 侧看到的 `deviceId`、UI 里看到的设备 ID 容易混淆。

为什么耗时：
- 测试 agent 会反复尝试错误的配对码，导致多轮无效验证。
- 发现层、二维码层、配对层的身份来源不一致，单靠 UI 很难判断错在哪里。

解决办法：
- 每次配对前必须先从 discovery 日志里抓当前会话真实的 `deviceId`。
- 以日志中的 `Handling discovered device: id=...` 作为配对目标唯一来源。
- 让 agent 强制记录：
  - 目标 serial
  - 发现到的 `deviceId`
  - 二维码里的 `deviceId`
  - 配对结果
- 不再依赖人工记忆或旧截图中的 ID。

### 2.2 relay 身份表和当前活跃设备混在一起

问题表现：
- relay 返回的 peers 里经常能看到历史残留设备。
- 同一个 relay 页面会同时出现 `probe`、旧设备、当前设备。
- 这会让测试 agent 错误判断“发现成功”，但其实拿到的是过期身份。

为什么耗时：
- agent 会基于旧身份继续尝试配对，导致重复失败。
- 需要额外做多轮核对才能确认当前会话的真实 peer。

解决办法：
- 每次发现后都重新拉一次 relay peers。
- 只认当前 discovery 日志和当前 UI 卡片，不认历史 peers。
- 给 agent 加规则：
  - 若 peers 中出现 `probe` 或历史残留，不得直接作为配对目标
  - 必须确认当前 `relay identity posted` 与 `discovered device` 是同一轮

### 2.3 设备重启后状态恢复与“连接态”不是一回事

问题表现：
- 重启应用后，已配对设备能恢复出来，但 UI 仍显示 `未连接`。
- 容易误判“重连失败”。

为什么耗时：
- 测试 agent 会把“配对状态持久化”误认为“实时连接已建立”。
- 如果没有明确连接触发点，重连验证就会卡在语义不清上。

解决办法：
- 明确区分三种状态：
  - 已配对
  - 已发现
  - 已连接
- 回归时必须单独验证：
  - 配对后重启能否恢复已配对设备
  - 重启后是否自动建立连接
  - 是否需要用户动作触发连接
- 若产品没有明确自动连接契约，agent 不能擅自把“恢复显示”判定为“重连成功”。

### 2.4 反复出现的构建破坏

问题表现：
- 在给代码加诊断日志时，曾因为换行处理不当导致 Kotlin 整块语法失效。
- 通过 PowerShell 写文件时，容易把注释和代码粘在一行，编译器报大量连锁错误。

为什么耗时：
- 一次小改动会变成整文件级编译失败。
- KSP / Kotlin 报错往往不是第一个真正出错点，定位成本高。

解决办法：
- 所有代码修改必须先用最小补丁。
- 先看 `git diff` 和源码行号，再改，不要直接做大段字符串替换。
- 添加文件前，先确认编码、换行和语法结构。
- 每次变更后先跑 `assembleDebug`，再跑 `testDebugUnitTest`。

### 2.5 设备预检和平台问题容易干扰业务判断

问题表现：
- 某些模拟器会出现 System UI ANR、启动焦点丢失、设备临时离线。
- 这些问题不是产品缺陷，但会阻塞验证。

为什么耗时：
- agent 如果不分层，就会把平台故障误判成业务 bug。
- 会浪费大量时间在错误方向上。

解决办法：
- 强制把问题分成：
  - 平台阻塞
  - 产品缺陷
  - 待确认
- 遇到平台阻塞时先切换设备，不要急着修产品代码。
- 每次 round 都先做健康设备数确认，只有健康设备满足条件才进入下一步。

## 3. 反复出现的问题

### 3.1 QR 配对码自动注入后仍需确认实际填充内容

问题：
- 调试码注入成功，不代表 UI 使用的是正确目标。
- 需要确认配对对话框中的 JSON 文本是否与当前发现到的 `deviceId` 一致。

解决：
- 让 agent 读取 UI tree，不只看截图。
- 必须核对配对框中的 `deviceId` 文本。

### 3.2 发现流程经常需要重新启动

问题：
- discovery 有时要先停止、重启、再等待 relay 数据刷新。
- 如果不重新拉取 logcat 和 UI tree，容易读到旧状态。

解决：
- 给 agent 增加固定的 discovery 轮次策略：
  - 清 logcat
  - 启动 discovery
  - 等待固定时间
  - 采集日志
  - 再 dump UI

### 3.3 单次验证后缺少“证据闭环”

问题：
- 只看操作过程不够，缺少结果证据会导致结论不稳。

解决：
- 每个关键步骤都要保存：
  - `adb logcat`
  - `uiautomator dump`
  - 当前焦点信息
  - 最终 UI 状态

## 4. 解决办法清单

### 4.1 测试执行层

- 统一使用以下顺序：
  1. `adb devices -l`
  2. `dumpsys window`
  3. `logcat` 清理
  4. 开始 discovery
  5. 等待 relay 更新
  6. 抓 UI tree
  7. 再执行配对 / 解除 / 重连
- 遇到失败时先分类，再决定是否修复代码。

### 4.2 证据层

- 所有结论必须绑定证据：
  - 目标 serial
  - 设备 ID
  - 结果日志
  - UI tree 结果
  - 构建结果
- 没有证据的“成功”不允许写入报告。

### 4.3 代码层

- 对测试友好的诊断点要保留，但不要破坏语法。
- 任何调试注入能力都要与真实业务路径隔离。
- 重构时优先使用最小侵入式修改。

## 5. 对测试 Agent 的升级建议

### 5.1 增加“身份对照”能力

Agent 必须能自动对照：
- discovery 日志中的设备 ID
- QR 码中的设备 ID
- relay peers 返回的 deviceId
- 当前选择的 UI 卡片

### 5.2 增加“状态分层”判断

Agent 必须区分：
- 平台健康
- 发现成功
- 配对成功
- 持久化成功
- 连接成功

### 5.3 增加“失败归因”规则

Agent 看到失败时，先判断是否属于：
- 模拟器平台问题
- 旧数据污染
- 调试码错误
- 产品逻辑错误

### 5.4 增加“编译前检查”

Agent 在写代码后必须先做：
- 源码结构检查
- 行级 diff 检查
- 编译验证

### 5.5 增加“重试边界”

Agent 对同一问题最多重复有限次数：
- 如果连续失败并且 ID 仍不一致，先切换证据源，不要盲试。

## 6. 结论

本轮最耗时的问题不是单一代码 bug，而是三类问题叠加：

1. 设备身份不稳定，导致配对目标反复选错
2. relay / UI / shell 三套身份来源没有统一
3. 小改动引发编译破坏，拖慢验证节奏

要升级测试 Agent，核心不是“多跑几次”，而是让它具备：
- 身份对齐
- 状态分层
- 证据闭环
- 失败归因
- 编译前检查

只有这样，后续 1-level / 2-level / 多设备回归才不会反复浪费在同类问题上。
