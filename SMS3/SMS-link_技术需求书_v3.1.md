# SMS-link 安卓应用技术需求书

**版本：v3.0（详细修订版 / AI Agent 执行约束版）**

**适用对象：** Claude Code、VS Code AI Agent、人工开发协同流程

---

## 一、文档定位与使用规则

本需求书用于约束 AI Agent 与人工协同开发过程，目标不是展示概念设计，而是为实际编码、调试、验收和迭代提供统一边界。文档中的条目默认均为必须满足项，但必须结合平台前提条件执行，避免 Agent 将 Android 系统级限制误判为应用层无条件可控能力。

本文档不允许被理解为"任意机型、任意 ROM、任意权限状态下都无条件成立"的绝对承诺。凡涉及默认电话应用角色、通知监听授权、前台服务、厂商电池优化策略、Wi‑Fi Direct 权限、蓝牙权限、系统后台调度机制时，必须在对应前提成立时按目标值验收，在前提不成立时按验收下限执行。

## 二、产品概述

| 项目 | 说明 |
|------|------|
| **产品定位** | 面向 Android 13 及以上设备的多设备协同个人工具，支持后续向 Windows/PC 扩展。 |
| **当前核心目标** | 通知镜像、短信协同、文件传输、通话伴随控制。 |
| **开发原则** | 离线优先、无服务器、Kotlin + Jetpack Compose、两台真机验收。 |
| **文档作用** | 作为 AI Agent 的开发约束文档，避免需求泛化、能力误判与盲目缝合开源代码。 |

SMS-link 是一款运行于 Android 13 及以上系统的多设备协同应用，面向用户手中的手机、平板和折叠屏设备，提供通知镜像、短信协同、文件传输和通话伴随控制四类核心能力。产品定位为可长期使用的个人工具，而非一次性演示原型，因此在设计时需强调可安装、可运行、可恢复、可维护、可扩展。

产品必须保持离线优先和无服务器原则，不依赖 GMS，不将移动数据网络作为当前版本的核心传输路径。当前版本的主要目标为 Android 与 Android 设备之间的直接协同，同时协议层必须预留平台中立设计，便于未来扩展到 Windows/PC 端。

## 三、系统范围与版本边界

当前版本的最低支持系统为 **Android 13（API Level 33）**。当前版本不要求 Android 11 或 Android 12 兼容，也不以公开商店上架为前提。应用以 APK 方式分发，可发布在个人 GitHub 账号中。

当前版本必须优先覆盖以下实际测试环境：至少一台一加手机、一台小米手机、一台 vivo 设备，以及一台 vivo 平板。设计时应以多厂商 ROM 差异为前提，避免仅在单一原生 Android 环境下成立。

### 当前版本的非目标

当前版本的非目标包括：
- 依赖远程服务器进行消息转发
- 支持跨公网中继
- 支持视频通话
- 支持第三方 VoIP 完整控制
- 支持桌面小组件
- 支持双卡复杂调度

相关能力可在后续版本扩展，但不得写入本版本刚性验收。

## 四、总体架构与通信原则

系统架构必须采用**控制平面与数据平面分离**的设计。BLE 仅承担发现、配对、轻量控制信令和状态同步，不承载大体积正文数据；局域网 Wi‑Fi 是首选主数据通道（L1）；当两台设备不在同一局域网下时，L2 降级策略按数据类型分叉：

- **对于文件传输和通话音频等大数据通道**：目标行为为自动开启移动热点并重新建立 Wi‑Fi 连接（前提：系统允许应用触发热点引导流程，或用户经提示后手动开启）
- **对于通知、短信、通话控制信令等轻量消息**：降级为蓝牙经典 RFCOMM 传输

蓝牙 RFCOMM 同时作为热点建立失败或用户拒绝后的最终兜底链路。

系统必须具备自动链路选择能力，默认优先级为：
```
L1 同一局域网 Wi‑Fi > L2-热点（大数据）/ L2-蓝牙（轻消息）> L3 蓝牙兜底
```

Wi‑Fi Direct 已从默认路径中移除，不得作为自动 fallback 目标。AI Agent 不得在未说明理由的情况下将 BLE 用于大文件传输，也不得将蓝牙当作默认高吞吐通道。

### 4.1 通信分层定义

| 层级 | 主要技术 | 用途 | 约束 |
|------|----------|------|------|
| **控制层** | BLE GATT | 设备发现、二维码配对确认、状态同步、轻量指令 | 不得传输文件正文 |
| **主数据层** | 局域网 Wi‑Fi | 通知、短信、文件的主通道 | 要求同一网络环境 |
| **L2-热点层** | 移动热点（Wi‑Fi） | 文件传输、通话音频等大数据通道的降级路径 | 需系统热点权限；目标行为为应用引导开启，前提条件单独标注 |
| **L2-蓝牙 / L3 兜底层** | Bluetooth RFCOMM | L2 轻消息降级（通知、短信、通话控制信令）；L3 热点失败后的最终兜底 | 吞吐有限，不适合大文件 |

## 五、设备角色模型

系统采用**"双角色模型"**，以避免主副角色与蜂窝能力的语义冲突。

1. **数据主设备**：负责通知、文件和控制逻辑的主要协同关系，可在应用内切换并保留原有配对关系、历史数据和密钥信息
2. **蜂窝能力源设备**：负责运营商短信与运营商语音通话，必须是当前具有有效 SIM 卡的设备

任一时刻只允许存在一个蜂窝能力源设备，但最多可连接四台副设备，且副设备之间不直接通信，只与主设备通信。角色切换后，系统必须重新计算同步方向与权限边界，并保留历史记录和信任关系。

本项目不要求双主设备，也不要求双卡复杂调度。若设备未插入可用 SIM，则不能承担短信与通话的真实源设备职责。

## 六、设备发现、配对与连接管理

设备发现与配对必须以**二维码为主要入口**。配对流程允许触发系统授权与系统弹窗，用户在发现到目标设备后，应能看到确认提示并完成配对。需求不再要求完全不跳系统设置页面，但要求核心流程可在应用中被引导完成。

连接管理必须支持自动重连，但不要求在首次发现阶段静默完成；系统在发现到对方后应弹出确认提示，再进入链路建立流程。应用不需要可信设备自动接收白名单机制，文件接收必须每次确认。

### 连接状态

连接状态需覆盖：
- 未连接
- 连接中
- 已连接
- 已断开
- 重连中

每种状态都必须在系统通知和应用内可见。

## 七、通知模块：通知镜像与有限交互

通知模块是当前版本的**最高优先级能力**。系统必须支持应用通知镜像，包括系统应用通知在内，但不覆盖前台服务常驻噪声通知、媒体会话控制通知等非目标类型，具体以可配置黑白名单控制。

### 核心功能

镜像后的通知必须完整显示：
- 来源设备名
- 应用名
- 应用图标
- 标题
- 正文
- 时间

并在副设备侧重新生成系统通知；用户点击后统一进入 SMS-link 内部详情页，而非强制跳回源应用。

### 同步策略

通知同步以实时通信为主，建立连接后还需补同步近 1 分钟内仍然活跃的通知，以及应用在本地缓存到的近 1 分钟通知事件。应用需长期保存通知历史，允许用户在设置或历史页中按条选择、批量选择或全部删除。

### 黑白名单

系统必须支持通知黑名单/白名单，并支持**"禁止双端应用同步"策略**。当目标设备也安装了指定应用时，该应用通知默认可被抑制；同时允许用户手动开启镜像，以覆盖默认抑制规则。

### 交互能力

通知交互能力只能在源通知自身提供标准 Action 或 RemoteInput 时才要求生效。对于未暴露标准动作的应用，仅要求查看和镜像，不强制要求回复、删除或标记已读。

### 敏感通知

验证码、银行通知、敏感业务通知仍属于可镜像范围，但在 Android 15 及更高版本中，系统可能对 OTP 类通知内容进行脱敏，应用只能在系统允许暴露原始内容的前提下显示完整信息。

## 八、短信模块

短信模块当前版本以 **SMS 为强制验收项**，MMS 仅作为协议与界面预留能力，不计入当前版本不通过条件。

### 核心功能

系统必须支持：
- 主设备接收短信提醒
- 副设备查看短信镜像
- 副设备通过主设备代发短信
- 短信已读状态同步
- 连接建立前近 1 分钟短信事件的补同步

### 非目标功能

当前版本不要求：
- 全量历史会话同步
- 联系人名优化
- 长短信拆分策略
- 群发增强能力

### SIM 卡选择

副设备发短信时必须允许选择主设备上的 SIM 卡位，但本项目假设仅存在一张用于流转的有效 SIM。

### 权限说明

系统不强制要求主设备成为默认短信应用；若系统权限和公开 API 能力导致部分会话管理功能受限，则以 Android 官方公开接口可实现范围为边界进行验收。验证码短信、银行短信、营销短信均属于可同步对象。

---

## 九、文件传输模块

### 核心功能

文件传输模块必须支持：
- 批量发送
- 从系统分享面板发起发送
- 接收前确认
- 应用内弹窗与系统通知双提醒
- 实时进度条
- 失败重试
- 传输结果反馈

当前版本优先保证文档、图片、视频三类文件的稳定传输。

### 链路策略

文件传输链路必须遵循固定策略：
```
L1 同一局域网 Wi‑Fi > L2 热点 Wi‑Fi > L3 蓝牙经典 RFCOMM
```

若设备不在同一 Wi‑Fi 下，则应引导用户开启移动热点并重新建立 Wi‑Fi 连接（目标行为：应用弹出提示引导开启；前提条件：系统允许触发热点引导流程，或用户手动操作）；若热点建立失败或用户拒绝，再回退到蓝牙 RFCOMM 链路。

**重要约束：**
- Wi‑Fi Direct 不再作为文件传输的备选路径
- BLE 不允许承载文件正文

### 文件大小

4GB 单文件上限属于目标值而非硬性验收下限，当前版本以稳定完成常见中等体积文件传输为主。接收目录、重名处理和覆盖策略可由实现方案自定义，但必须向用户给出明确反馈。

## 十、通话模块：通话伴随控制与协同

通话模块名称统一修改为**"通话伴随控制与协同"**，避免将其误解为完全接管系统电话栈的系统级能力。当前版本仅面向运营商语音通话，不包括视频通话，不包括微信、WhatsApp 等第三方 VoIP 的完整控制。

### 验收阶段划分

本模块当前版本的验收重点明确拆分为两个阶段：

#### 第一阶段（当前版本刚性验收）：通话控制能力

当主设备将 SMS-link 设置为默认电话应用并完成必要授权时，副设备可接收来电通知并执行接听、挂断、静音、保持等控制动作；控制信令在 L1 下走 TCP 主通道，L2 降级时走蓝牙 RFCOMM。

对于副设备主动拨号，当前版本仅做结构预留，不作为验收必选项。

#### 第二阶段（目标能力，独立分支开发）：通话音频双向传输

不纳入当前版本主工程迭代节奏，待控制能力稳定后作为独立实验分支推进。

**实现前提：**
- 默认电话应用角色已授予
- 公开 Android 电话接口可用
- 当前测试机型的 ROM 与音频路由策略允许此路径成立

**音频传输通道：**
- 仅走 L1 局域网 Wi‑Fi（UDP）
- L2 热点 Wi‑Fi 可作为补充
- 不经蓝牙传输音频

AI Agent 在进入第二阶段开发前，必须先独立验证 InCallService 控制路径在至少两台真机上稳定可用。

### 性能指标

通话延迟 200ms 为目标值，不作为所有场景和所有机型的绝对硬下限。通话模块的正式验收必须基于至少两台真机，且其中至少一台为实际插卡主设备。

## 十一、后台保活与恢复机制

应用必须支持：
- 前台服务常驻
- 后台同步
- 自动重连
- 系统通知常驻提示

首次配对与授权完成后，只要系统未强制回收核心前台服务，用户即使未主动打开应用，也应继续接收通知和消息同步。

### 权限引导

应用需明确引导用户授予：
- 忽略电池优化
- 自启动
- 后台白名单

但需求书不再将"任何后台场景下必然长连"写为无条件承诺，而是要求在这些前提成立时尽量保持实时性优先。

### 恢复机制

设备重启或进程重建后，系统允许在前台服务恢复后继续同步，不要求用户每次都重新完整配对。若用户主动撤销配对或系统清除权限，则允许要求重新授权。

---

## 十二、安全、隐私与数据策略

当前版本采用普通局域网可信设备加密，不引入复杂的端到端密钥体系说明。文档不再描述具体密钥协商细节，以避免 AI Agent 误将复杂密码学体系作为当前版本刚性目标。

### 数据存储

同步后的本地通知、短信和相关历史数据默认不加密存储，此项为明确设计选择，而非遗漏。应用需支持主设备侧撤销某个已配对副设备，并允许设备断连后已同步历史继续保留。

### 权限管理

当前版本不提供按设备细分授权范围功能，不做"某设备只能看通知不能看短信"的细颗粒权限分配。

---

## 十三、界面与交互要求

应用界面应按正式消费级产品标准设计，技术栈固定为 **Kotlin + Jetpack Compose**。当前版本必须同时兼顾手机、平板和折叠屏三类形态，不接受仅优先手机、其他形态仅"可用但不优化"的方案。

### 必需页面

界面至少应包含：
- 设备连接管理页
- 通知历史页
- 短信页
- 文件传输页
- 设置页
- 权限引导页
- 诊断日志页

诊断日志页主要面向开发和测试使用，但需在应用内保留入口，便于排查问题。

### 国际化与主题

系统必须支持：
- 中英文切换
- 暗黑模式

桌面小组件作为后续升级项，当前版本不纳入刚性验收。

---

## 十四、协议与跨平台扩展要求

鉴于产品后续需兼容 Windows/PC，协议层必须采用**平台中立设计**，推荐使用 JSON 或 Protobuf 描述统一消息结构，不得将核心协议直接绑定为 Android 专有对象或仅能在应用进程内反序列化的结构。

### 消息结构

所有跨设备消息均应包含基础字段：
- 消息类型
- 发送设备标识
- 接收设备标识
- 时间戳
- 消息版本
- 负载内容
- 错误码或状态字段

以便未来桌面端接入。

## 十五、AI Agent 开发约束

### 统一执行规则

**AI Agent 在开始任一模块开发前，必须先读取本需求书、输出模块理解摘要、列出前提条件、说明拟参考的 GitHub 仓库仅用于思路学习而非直接复制，并给出真机测试方案后方可进入编码阶段。**

### 代码使用约束

AI Agent 仅可将参考 GitHub 仓库用于：
- 功能分析
- 目录结构参考
- 协议思路学习
- 类职责提炼
- 交互流程对照

**不得将参考仓库代码整仓复制或直接拼接到主工程中。** 除许可证明确兼容外，任何受限代码都不得直接进入最终公开发布工程。

需求书中必须明确禁止整仓复制 GPL 等强约束许可证代码进入主工程。

### 开发流程

AI Agent 每开发一个模块，都必须先给出：
1. 模块理解
2. 依赖权限
3. 风险点
4. 拟参考仓库
5. 测试步骤
6. adb 日志抓取方式与成功标准

再进入编码。

### 测试策略

允许 Agent 先建立 mock 通道或伪设备流程验证业务逻辑，再接入真实蓝牙和 Wi‑Fi Direct，但最终交付必须以真实双机测试结果为准。

## 十六、性能指标与验收方式

本项目的性能指标采用**"目标值 + 验收下限"**的表达方式。

| 模块 | 目标值 | 验收下限表达 | 说明 |
|------|--------|--------------|------|
| **通知镜像** | ≤ 500ms | 在前提条件成立时尽量接近目标值 | 以实时性优先，不以离线补同步替代实时推送 |
| **通话控制** | ≤ 200ms | 在默认电话应用前提下验证控制可用 | 音频路由受平台限制，按测试机型结果验收 |
| **文件传输** | 单文件 4GB | 以中等体积文件稳定传输为当前基础 | 4GB 为目标值，不作为首版硬拒收标准 |

通知镜像延迟以 500ms 为目标值；通话控制延迟以 200ms 为目标值；文件传输中 4GB 为单文件目标上限；这些数值可作为优化方向，但不得脱离平台前提条件进行绝对化承诺。

---

## 十七、真机测试与交付标准

最终交付不得仅以"可以编译通过"作为完成标准，必须达到**"两台真机可运行 + 核心功能可验证 + 输出测试报告"**的交付要求。

### 测试报告要求

测试报告至少应包含：
- 测试设备清单
- 系统版本
- 权限状态
- 关键链路
- 成功步骤
- 失败现象
- 日志抓取命令
- 修复记录

### 最小可复现实验路径

每个核心模块都应提供最小可复现实验路径。例如：
- **通知模块**：需说明如何授予通知监听并观察双机镜像
- **文件模块**：需说明如何在同网与非同网环境下切换链路
- **通话模块**：需说明默认电话应用的设置路径和最小测试流程

### 交付质量标准

交付时应用必须：
- 无明显崩溃
- 无关键页面打不开
- 无核心功能完全失效的情况

若某些能力依赖前提条件，则必须在文档和应用引导中明确提示，不得隐藏。
